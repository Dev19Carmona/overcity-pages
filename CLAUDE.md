## Architecture

`create-next-app` project (App Router, TypeScript, Tailwind v4, React 19) that serves the OverCity links page and an admin panel to edit it.

- `/` (`app/page.tsx`) renders `app/_components/site-view.tsx` with `getPublicContent()` (`"use cache"`, tag `content`). Falls back to `DEFAULT_CONTENT` in `lib/links.ts` if Redis is empty or fails.
- `/admin` (`app/admin/`) is the single admin panel. `layout.tsx` shows the SSO entry screen (`Entrar con tu cuenta`) without a session, "Sin permiso" with a session that has no admin permission, and otherwise wraps every admin page in a sidebar (≥900 px) / top bar (mobile) with `AdminNav` (filtered by permission; `Página de links`, and under `Catálogo`: `Productos`, `Categorías`, `Colores`, `Ajustes del catálogo`), links to the site and the store, and logout. `/admin` itself (`app/admin/page.tsx` → `_components/links-admin.tsx`) is a form for the links page: logo, texts, link buttons, socials, background, music and effects; nothing is published until `Guardar` (the logo is published on upload). There is no WYSIWYG edit mode anymore. `app/admin/_lib.ts` has `loadAdminContent()` and the catalog loaders `loadAdminList()` / `loadAdminColors()` / `loadAdminSettings()` / `loadAdminEditor(id)` (null without the screen's permission); shared admin UI pieces live in `app/admin/_components/ui.tsx`. `saveContent` (`app/admin/actions.ts`) validates, writes to Redis and calls `updateTag("content")`.
- Auth (SPEC 13): `/admin` login is delegated to base-template (OIDC Authorization Code + PKCE, contract `sso-v1`); there is no shared password anymore. `lib/sso/` is a standalone OIDC client (`pkce.ts`, `crypto.ts` AES-256-GCM, `flow-cookie.ts` for the encrypted `overcity_oidc` flow cookie and `sanitizeReturnTo`, `tokens.ts` ES256 verification with `jose`, `client.ts` authorize URL/code exchange/refresh/revoke/JWKS and `readSsoConfig()`); it must not import Overcity code. `GET /auth/login` and `GET /auth/callback` (`app/auth/`) run the flow; errors come back as `/admin?error=<code>` (fixed map in `login-screen.tsx`). The session is an opaque cookie `overcity_session` + Redis record `overcity:session:<sid>` (`lib/session.ts`: refresh token encrypted, 7-day absolute limit, refresh when the access token has <30 s left under a Redis lock `overcity:session-lock:<sid>`; IdP down = deny without deleting; `invalid_grant` = delete). `lib/auth.ts` exposes `getSession()` (per-request cached), `requirePermission(permission)` (401/403 for routes and actions), `startSession`, `logout`, and re-exports `can`, `hasAnyAdminPermission`, `firstAllowedPath` from `lib/permissions.ts`, which holds the permission catalog: `links.contenido.editar`, `catalogo.productos.editar`, `catalogo.categorias.editar`, `catalogo.colores.editar`, `catalogo.ajustes.editar` (a new permission must also be registered in base-template with `PUT /platform/modules/:key`). Every Server Action, loader (`_lib.ts`) and Route Handler checks its permission; hiding a link protects nothing. Admin pages show `NoPermission` (HTTP 200) when the loader returns null with a session. Tests (Vitest) live in `tests/`.
- `app/api/logo/route.ts` uploads and removes the logo in Vercel Blob.
- Social networks are a list (`socials`, max 8) chosen from the fixed catalog in `lib/socials.ts`, rendered as a horizontal row of icons (`app/_components/social-icon.tsx`). In `/admin` each network is a row with its URL, ↑ ↓ and `Quitar`.
- Content lives in Redis under `overcity:content:v2`. If it does not exist, `overcity:content:v1` (the SPEC 02 shape with `instagramUrl`) is read and converted in memory; `v1` is never modified.
- Background, music and effects are editable (SPEC 05): `SiteContent` has `background` and `music` (`MediaSetting` = `{ source: "default" | "custom" | "none", url }`) and `effectsEnabled`. `default` = the `public/overcity/` assets (`lib/media.ts`), `custom` = a Vercel Blob URL (validated as `https://*.blob.vercel-storage.com`, max 500 chars), `none` = plain navy background / no music button. Missing fields in stored `v2` are filled with defaults on read (same key). `effectsEnabled: false` does not render `SceneEffects`.
- `app/api/media/route.ts` hands out Vercel Blob client-upload tokens (`handleUpload`) only with a session that has `links.contenido.editar` (401 without session, 403 without the permission), restricted by path prefix: `background/` (PNG/JPG/WebP, max 5 MB) or `music/` (MP3, max 15 MB); limits live in `lib/content-limits.ts`. Catalog photos no longer go through this route (SPEC 12: `/api/catalog-media`, below). The browser uploads straight to Blob from `app/admin/_components/media-uploader.tsx` (the 11 MB default MP3 exceeds Vercel's ~4.5 MB function limit); it does not rely on `onUploadCompleted`. Uploading, removing or restoring only changes the draft; `saveContent` deletes the previous Blob file when a `custom` value is replaced (never `public/` assets).
- Product catalog (SPEC 06, reshaped by SPEC 07, moved to Supabase by SPEC 12) lives apart from `SiteContent`, in Supabase: Postgres tables for the data and Storage for the design photos. Redis and Vercel Blob no longer hold the catalog (see *Catalog storage* below). `lib/catalog.ts` (server-only) is the data layer: reads `getPublicCatalogList()` and `getPublicProduct(id)` (`"use cache"`, tag `catalog`, visible products only), `getAdminCatalogList()`, `getAdminProduct(id)`, `getAdminCategories()`, `getAdminColors()`, `getAdminEditorMeta()`, `getAdminSettings()` (uncached) and `readProducts(ids, onlyVisible)`; writes `writeProduct`, `removeProduct`, `writeProductVisible`, `writeProductMove`, `writeCategories`, `writeColors`, `writeSettings` (each calls an RPC) plus `deleteUnreferencedImages`. Validation is split by entity in `lib/catalog-validate.ts` (no `server-only`, also used by the migration script): `validateProduct`, `validateCategories`, `validateColors`, `validateSettings`, and `validateCatalog` (whole catalog, only for the script). `lib/catalog-shared.ts` holds the types (`Catalog`, `CatalogProduct`, `CatalogDesign`, `CatalogColorDef`, and the light read types `ProductCard`, `CatalogList`, `VersionedProduct`, `ColorUsageMap`), the color types and helpers (SPEC 11, below), sizes (`CATALOG_SIZES` XS–XL, `ONE_SIZE` "Única"), `sizesFor`, the stock helpers (`emptyStock(colors, sizes)`, `stockOf(product, designId, color, size)`, `colorStock(design, color)`, `designStock`, `stockTotal(product)`, `productColors(product, colors)`, `coverImage`, `resizeStock`, `sortSizes`), `normalizeText`, `CATALOG_CURRENCIES` and `formatPrice` (client-safe). Model: `Catalog` = `{ title, currency, whatsapp, freeShippingFrom, categories[], colors[], products[] }`; a category has `id`, `name` and `oneSize`; a product has `name`, `description`, `price` (integer or null), `categoryId` (or null), `visible` and 1–`MAX_DESIGNS` (20) `designs` (SPEC 10; first = cover). A design (`CatalogDesign`) is `{ id, name, image, colors, stock }`: `id` stable inside the product (`crypto.randomUUID()` like product and category ids), `name` required, 1–`MAX_DESIGN_NAME` (40) chars and unique inside the product (compared without case or accents; it is what WhatsApp shows; also a `unique (product_id, name_key)` in the database), `image` one public Supabase Storage URL, `colors` 1–`MAX_DESIGN_COLORS` (10) from the color list and `stock[color][size]` (one integer 0–9999 per color × size; first-level keys must be exactly the design's `colors`, second-level keys exactly `sizesFor(category)`; `jsonb` does not keep key order, so reads rebuild colors in the design's order and sizes with `sortSizes`). In the store, the product page (`product-detail.tsx`) has a design selector (thumbnails with the design name as accessible label) and shows only the colors of the chosen design; sizes are crossed out according to design + color, a color with no stock in any size is crossed out but still selectable; it starts on the first design with stock and on that design's first color with stock; changing design keeps the color if it exists in the new design (otherwise the first color with stock) and deselects a size without stock. The store list works on light cards (`ProductCard`: `cover`, `coverColor`, `hoverImage`, `designCount`, `colors`, `stockTotal`; no description and no stock matrix, so the `/catalogo` HTML stays small); `AGOTADO` uses `stockTotal` (computed in SQL). Limits in `lib/content-limits.ts`: `MAX_PRODUCTS` 500, `MAX_CATEGORIES` 50, `MAX_DESIGNS` 20 (one photo each), `MAX_COLORS` 60, `MAX_DESIGN_COLORS` 10, `MAX_DESIGN_NAME` 40, `MAX_PRODUCT_IMAGE_BYTES` 5 MB (PNG/JPG/WebP), `MAX_STOCK` 9999 (a product tops out at 20 designs × 10 colors × 5 sizes = 1000 cells).
- Catalog storage (SPEC 12): schema in `supabase/migrations/0001_catalog.sql`, applied by hand in the Supabase SQL Editor (safe to re-run): tables `catalog_settings` (single row), `categories`, `colors` (`name` is the primary key, `name_key` unique), `products` (`position`, `version`), `designs` (`image_path`, the path inside the bucket, not the URL), `design_colors` (FK `on delete restrict` on `colors`, so a used color cannot be dropped) and `design_stock`; RLS is on in every table with no policies, and `anon`/`authenticated` have no privileges, so only the service role reads or writes. Only the server talks to Supabase (`lib/supabase.ts`, `SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY`, never `NEXT_PUBLIC_`); the browser only uploads a photo to a signed URL. Writes are RPCs (all `security invoker`, one transaction each, returning `{ ok, error?, version? }`): `save_product(payload, expected_version)` (creates when `expected_version` is null; replaces designs, colors and stock; bumps `version`; `error = 'conflict'` when the stored version differs and nothing is written), `delete_product`, `set_product_visible` (bumps `version`), `move_product` (swaps `position`, no version bump), `save_categories` (syncs the list; a deleted category leaves its products uncategorized with XS–XL; a changed `one_size` resizes stock in the same transaction with the `resizeStock` rules, via `resize_product_stock`, and bumps those products' `version`), `save_colors` (a used color fails with `color_in_use`; `writeColors` turns it into the message with the count) and `save_settings`. Read RPCs: `catalog_cards(only_visible)` (light cards, `stock_total` summed in SQL), `catalog_products(ids, only_visible)` (full products as `jsonb`) and `catalog_color_usage()`. Optimistic concurrency is only on products: `saveProduct(product, expectedVersion)` returns `Este producto cambió desde que abriste la ficha. Recarga para ver la versión nueva.` on conflict and the open draft is kept on screen; categories, colors and settings save immediately without versions. After a successful write the action deletes from Storage the photos no design references any more (`deleteUnreferencedImages`, looks at `designs.image_path`) and calls `updateTag("catalog")`. Photos: public bucket `catalog` (5 MB and PNG/JPG/WebP enforced by the bucket itself); `POST /api/catalog-media` (session required, 401 otherwise) validates type and size and returns `{ path, signedUrl, publicUrl }` for a server-generated `catalog/<uuid>.<ext>` (`createSignedUploadUrl`), and `product-designs.tsx` PUTs the file to `signedUrl` (multipart, with progress). A valid image URL starts with `SUPABASE_URL/storage/v1/object/public/catalog/` (`isCatalogImageUrl`); images use `unoptimized`, so `next.config.ts` needs no remote host. There is no fallback with default data when Supabase is down: cached store pages keep serving and the panel shows an error. Migration: `scripts/migrate-catalog-to-supabase.ts` is a one-off, idempotent script (`npx tsx --env-file=.env.local scripts/migrate-catalog-to-supabase.ts [--dry-run]`) that reads `overcity:catalog:v2` (or `v1`) from Redis through `lib/catalog-legacy.ts` (the old `v1`→`v2`, SPEC 09 and SPEC 10 in-memory conversions, no `server-only`), copies each photo from Blob to Storage under a deterministic path (`catalog/<sha1 of the original URL>.<ext>`), upserts the rows and verifies counts, per-product stock totals and that each photo answers 200. It never modifies or deletes anything in Redis or Blob. Rollback: the old data stays untouched, so redeploying the commit before the cut serves the catalog from Redis and Blob exactly as it was when the script ran (edits made in Supabase after the cut are not copied back). The `overcity:catalog:*` keys and the `catalog/` files in Blob are now only a backup of the cut and are meant to be cleaned in a later spec.
- Catalog colors (SPEC 11): the fixed palette is gone. `Catalog.colors` is a list of `CatalogColorDef` `{ name, hex, hidden }` (max `MAX_COLORS` 60; `name` 1–`MAX_COLOR_NAME` 24 chars, unique without case or accents, `hex` `#RRGGBB`), stored in the `colors` table (SPEC 12; before that, in `overcity:catalog:v2`). `CatalogColor` is just a `string` = the color's `name`, which is the **stable identifier** used by `design.colors`, `stock`, `CartLine.color` and the WhatsApp message; it cannot be renamed (no cascade). `DEFAULT_COLORS` (Negro, Blanco, Rojo, Navy, Gris, Arena) is only the seed used when converting old catalogs in the migration script. `validateProduct` rejects a design color that is not in the list, and the foreign key makes the database refuse to drop a used color; `saveColors` (`app/admin/catalogo/actions.ts` → `writeColors`) returns an error with the count of designs/products when deleting a used color. `hidden` colors are not offered when picking colors for a design, but designs that already have them keep them (product sheet offers visible + the design's own, in list order; max `MAX_DESIGN_COLORS` 10 per design). Helpers in `lib/catalog-shared.ts`: `DEFAULT_COLORS`, `colorHex(colors, name)` (`#808080` if missing), `colorUsage(catalog, name)` (used by tests; the panel reads `catalog_color_usage()`), `productColors(product, colors)`. `CartShell` carries `colors` (`name`, `hex`) so the bag paints thumbnails without constants. Admin page: `/admin/catalogo/colores` (`colors-admin.tsx`: create with picker + hex, edit hex, ↑↓, `Oculto` switch, `Eliminar` disabled when in use, `<dialog>` confirm).
- Store routes (SPEC 07): `/catalogo` and `/catalogo/[id]` use `app/_components/store-shell.tsx` (background and effects from `SiteContent`, sticky header with logo, brand, nav and the bag button; no music button, no admin lock) and are wide (`STORE_WIDTH`, up to 1240 px). `/catalogo` renders `app/catalogo/_components/catalog-browser.tsx` (client: search without accents by name and category, sort Destacados/precio, category chips, `?categoria=<id>` read with `useSearchParams` inside `Suspense` whose fallback is the unfiltered view so the first HTML already has the products). `/catalogo/[id]` renders `_components/product-detail.tsx` (design gallery, color and size pickers, quantity, `Agregar a la bolsa` and `Preguntar por WhatsApp`); the product comes from `getPublicProduct(id)` and hidden or unknown ids call `notFound()`; `generateStaticParams` returns visible ids (from `getPublicCatalogList()`) or a placeholder because `cacheComponents` rejects an empty list; the first request to an id never seen before streams with status 200 and the 404 content, later ones answer 404. The home shows an automatic first button to `/catalogo` (text = catalog title) and, below it, one button per category with visible products (cover of its first product, name, count, link `/catalogo?categoria=<id>`) only if there is at least one visible product; none are `LinkItem`s nor count toward the 20-link limit (`catalogLabel` and `catalogCategories` props of `SiteView`).
- Catalog admin (SPEC 07), `/admin/catalogo` inside the `/admin` layout: `page.tsx` (products list: search, category chips, Visible switch, ↑↓ order), `categorias/page.tsx` (create, rename, ↑↓, `oneSize` switch, delete with `<dialog>`), `ajustes/page.tsx` (title, currency, WhatsApp number and free-shipping threshold), `producto/[id]/page.tsx` (`nuevo` creates; editor in `_components/product-editor.tsx` + `product-designs.tsx`: `Diseños` section with up to 20 designs, drag-and-drop upload (each photo becomes a design `Diseño N`), name, own colors, ← → arrows and `Quitar` with undo; `Stock por diseño, color y talla` section with one collapsible table per design and totals per color, design and overall). Each page checks its permission through `_lib.ts` (`loadAdminList()`, `loadAdminColors()`, `loadAdminSettings()`, `loadAdminEditor(id)`; they return null without a session). Server actions in `app/admin/catalogo/actions.ts` (`saveCatalogSettings`, `saveCategories`, `saveColors`, `saveProduct(product, expectedVersion)`, `deleteProduct`, `setProductVisible`, `moveProduct`): every one requires its permission (SPEC 13), validates its entity, calls the RPC, deletes Storage photos nobody uses any more and calls `updateTag("catalog")`. List-style actions answer with the light `CatalogList` (not the whole catalog), `saveColors` with colors + usage and `saveProduct` with the validated product and its new `version`. Saving is per product sheet; categories, settings and visibility are saved immediately. Photos go through `/api/catalog-media` (5 MB per image).
- Shopping bag (SPEC 08): `Catalog` also has `whatsapp` (digits only with country code, 8–15, `""` = not configured) and `freeShippingFrom` (integer or null), both edited in `/admin/catalogo/ajustes` (`saveCatalogSettings` normalizes the number with `normalizeWhatsapp`); missing fields in stored `v2` default to `""`/`null` (same key). The bag is client-only: `localStorage["overcity:cart:v1"]` = `{ lines: CartLine[] }` (`{ productId, designId, color, size, qty }` (SPEC 10), qty ≤ stock of that design + color + size via `lineStock(product, designId, color, size)`, max `MAX_CART_LINES` = 30; a line is product + design + color + size; `readCart` tolerates old lines without `designId` and `reconcileCart` drops them, and lines whose design/combination no longer exists or has no stock, with the existing `Actualizamos tu bolsa…` notice; the key `overcity:cart:v1` did not change). `lib/cart.ts` has the pure logic (read/write, `reconcileCart`, `addLine`, `setQty`, totals, `buildOrderMessage`, `buildInquiryMessage`, `whatsappUrl`). Order message lines: `N. {name} — Diseño: {design} — {color}, {size} × {qty} — {total | Consultar}` plus the product URL; the inquiry message adds `Diseño: …` only when a design is chosen. The drawer shows the design photo and `Diseño · Color · Talla`. `store-shell.tsx` passes only a `CartShell` (colors, currency, WhatsApp, free-shipping threshold, brand name) and, on a product page, that product (`pageProducts`, so it can be added at once) to `app/_components/cart-provider.tsx` (SPEC 12: it no longer receives the catalog; after mount and when another tab changes the bag it calls the server action `getCartProducts(ids)` in `app/_actions/cart.ts`, which returns the same summary as before — `designs` with `id`, `name`, `image`, `colors`, `stock` — only for the products in the bag (max 30), then reconciles; if the server does not answer the bag stays as stored and a notice is shown; it also syncs tabs via `storage`, holds the toast and the `Prenda quitada · Deshacer` undo); `cart-button.tsx` is the header button and `cart-drawer.tsx` a `<dialog>` drawer (top layer, so it sits above everything; the toast is rendered inside it while open). `Enviar pedido por WhatsApp` opens `https://wa.me/<number>?text=…` in a new tab with the origin taken from `window.location`; without a number the bag still works but the button is disabled. No checkout, no orders, stock is never decremented, no shipping cost (the free-shipping bar is only a progress message).
- `lib/content.ts` holds the `SiteContent` types, validation and Redis access; `lib/auth.ts` holds the signed session cookie and login rate limit; `lib/redis.ts` is the shared Upstash client. `lib/supabase.ts` is the server-only Supabase client (service role) and `lib/catalog.ts` the catalog data layer.
- Content that changes over time (texts, links, images) must live in `SiteContent` and be editable from the panel (see `specs/02-admin-de-contenido.md`).

## Environment variables

Copy `.env.example` to `.env.local` for local development. In Vercel, `KV_REST_API_*` and `BLOB_READ_WRITE_TOKEN` come from the Upstash Redis and Blob integrations; `APP_URL`, `AUTH_*`, `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` are added by hand in Settings → Environment Variables.

- `APP_URL`: canonical public URL of Overcity (used for the OIDC `redirect_uri`; never derived from `Host`).
- `AUTH_ISSUER`, `AUTH_CLIENT_ID`, `AUTH_CLIENT_SECRET`, `AUTH_TENANT_ID`: base-template SSO (issuer URL, registered client, company UUID). The secret is server only.
- `AUTH_SESSION_SECRET`: min 32 chars; encrypts the `overcity_oidc` cookie and the refresh token stored in Redis.
- `ADMIN_PASSWORD`, `ADMIN_SESSION_SECRET`: obsolete (SPEC 13); kept in Vercel only until the production cut is verified, then removed.
- `KV_REST_API_URL`, `KV_REST_API_TOKEN`: Upstash Redis (content and admin sessions).
- `BLOB_READ_WRITE_TOKEN`: Vercel Blob (logo, background and music; no longer the catalog photos).
- `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`: Supabase (catalog tables and photo Storage). Server only, never `NEXT_PUBLIC_`; the service role key lives only in `lib/supabase.ts`.

Without Redis the public page still works with the defaults, but `/admin` cannot open sessions; if any `AUTH_*`/`APP_URL` variable is missing, login answers `not_configured`. Without Supabase the catalog has no fallback: the store pages already cached keep serving and the catalog panel shows an error.

Non-default setup worth knowing:

- `next.config.ts` enables `cacheComponents` and `partialPrefetching`, plus `experimental.agentFeedback`. `cacheComponents` changes the caching/rendering model, so consult the bundled docs before using data fetching, `"use cache"`, or dynamic APIs.
- Tailwind is wired through Turbopack: `turbopack.rules` in `next.config.ts` runs `*.css` through `@tailwindcss/turbopack`.
- The root layout uses the globally generated `LayoutProps<"/">` type (no import needed); route types come from `.next/types` / `.next/dev/types`, included in `tsconfig.json`.
- Path alias `@/*` maps to the repo root (not `src/`).
- `tsconfig` has `strict: true`.
